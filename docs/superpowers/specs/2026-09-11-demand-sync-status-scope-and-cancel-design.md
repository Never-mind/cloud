# 需求单同步：状态范围扩展与"远端取消"处理方案

编写日期：2026-09-11
涉及服务：`src/lib/frappe-demand-sync-service.ts`、同步台账与映射页

## 一、状态范围扩展

### 1.1 现状

同步只拉取 `Committed`：`hasEligibleStatus()` 读环境变量 `FRAPPE_DEMAND_ELIGIBLE_STATUS`，默认值 `Committed`，其它状态直接跳过（本机未配置该变量，走默认值）。

远端实际状态共 8 种，当前 277 条明细的分布：

| 状态 | 条数 |
| --- | ---: |
| Received | 148 |
| Committed | 96 |
| Cancelled | 30 |
| Handed Over | 2 |
| Shipped | 1 |

（另 3 种 Issued to Supplier、Confirmed、Arrived 当前样本中还没有，需要一并支持。）

### 1.2 目标

1. 8 种状态都要**进入本地台账**（可追溯）；
2. 除 Cancelled 外，其余 7 种都要**创建本地需求草稿**；
3. Cancelled **不建单、不计入"待处理"、不显示红点**。

### 1.3 设计：把状态分成三类

| 分类 | 状态 | 行为 |
| --- | --- | --- |
| 建档 | Issued to Supplier、Confirmed、Committed、Handed Over、Shipped、Arrived、Received | 创建本地需求草稿，台账记 `synced` |
| 取消（终态） | Cancelled | **只写台账**（`cancelled`），不建单、不计入待处理、不进红点徽标 |
| 未知 | 其它新状态 | 记 `out_of_scope` 并在同步结果里提示（属于数据维护问题） |

配置项（部署文档同步更新）：

```env
FRAPPE_DEMAND_SYNC_STATUSES=Issued to Supplier,Confirmed,Committed,Handed Over,Shipped,Arrived,Received
FRAPPE_DEMAND_CANCELLED_STATUSES=Cancelled
```

### 1.4 关键实现点

- **取消明细必须在分组前分流**：实测 30 条 Cancelled 明细的数量全部为 0，而建档流程要求 `数量 > 0`，直接放进建档流程会被判成 `blocked`，变成一堆无意义的待处理。
- 取消明细写台账时 `status = 'cancelled'`，并记录"远端已取消，不创建本地需求单"。
- 若某张单只有取消明细，同步结果里给一条**信息行**（不计入 blocked / changed）。
- 台账视图与红点徽标口径同步调整：`cancelled` 不算未处理。

### 1.5 风险

拉取范围扩大后，**首次同步会新建大量草稿**：可建档明细从 96 条增加到约 247 条（277 − 30 取消），涉及的需求单数量需要先算出来。建议：

1. 先跑「试运行」核对将新建多少张单；
2. 必要时分批放开（先按国家或批次）；
3. 生产环境在维护窗口操作，先备份。

## 二、远端取消已建单的需求单，怎么提示用户

### 2.1 场景

本地已经建过需求单（可能是草稿、待下单或已下单），远端对应明细后来变成 Cancelled——**本地需求单按理也应取消**。

本地数据现状（说明为什么不能自动处理）：需求单 239 张，其中**已下单 222 张**；下游已有 274 行月账单台账、1 条预付款合同明细、278 条已确认采购明细引用着这些需求单。

### 2.2 方案：检测 → 提示 → 人工确认处理（不做全自动）

**第 1 步 检测**

同步时发现：某条明细在台账里是"已跟踪"（synced / skipped_existing / pending_change），而本次远端状态变为取消 → 台账标记为 `remote_cancelled`，记录取消的明细与本次状态。

**第 2 步 提示**（多入口，确保看得见）

1. 「同步台账」标签的**红点徽标**把这类单计入"待处理"；
2. 台账列表该行显示红色状态「**远端已取消**」，并显示影响的明细数；
3. 同步结果逐单给出提示，文案示例：

   > DO-00012 远端已取消 2 条明细；本地需求单 eSHWC26072309vw 状态为「已下单」，请确认是否需要取消。

4. 展开明细可以看到具体是哪几条明细（明细号 + 原状态 + 现状态）。

**第 3 步 处理动作（人工触发，支持多选）**

台账里勾选后点「**取消本地需求单**」：

| 本地需求单情况 | 处理 |
| --- | --- |
| 草稿 / 待下单，且未被采购、预付款、月账单引用 | 允许取消（复用现有 `deleteRequestOrder`，它已内置"已生成月账单/预付款则拒绝"的校验） |
| 已下单，或已被采购/月账单/预付款引用 | 按钮禁用并给出原因：「该需求单已生成采购订单/月账单，请先在下游流程处理」 |

取消成功后台账状态更新（`cancelled`），红点数量相应减少。

**为什么不做全自动**：222 张本地单是"已下单"状态，下游有采购订单、月账单台账、预付款明细引用；自动删除或改状态会破坏单据链和财务对账，必须由业务确认。

**可选增强（默认关闭）**：只对"草稿 + 无任何下游引用"的单开启自动取消开关，其余仍走人工确认。

### 2.3 反向场景

远端取消后又恢复（Cancelled → Committed）：

- 台账该明细从 `cancelled` 恢复为可建档状态，会按新单重新创建草稿，并在同步结果里提示「远端已恢复，已重新创建草稿」；
- 若本地单此前还是草稿（未做任何处理），重新创建不会产生重复档案（台账以明细为键）。

## 三、实施步骤与工作量

| 步骤 | 内容 | 预估 |
| --- | --- | --- |
| 1 | 状态分类配置 + 分流逻辑（取消类只记台账、未知状态记 out_of_scope） | 0.5 天 |
| 2 | 台账 `cancelled` / `remote_cancelled` 状态展示、筛选与红点口径调整 | 0.5 天 |
| 3 | 取消提示（同步结果 + 台账行提示 + 明细展开） | 0.5 天 |
| 4 | 「取消本地需求单」动作（下游引用校验、批量、与现有删除策略复用） | 1 天 |
| 5 | 试运行影响清单核对 + 回归测试 | 0.5 天 |

合计约 **3 天**。

## 四、待确认问题

1. 建档状态是否就按上述 7 种全部放开（尤其 Received / Arrived / Shipped / Handed Over 这类已完成状态也要建草稿）？
2. Cancelled 是否也写台账（建议写，便于追溯；不写就完全看不到取消过）？
3. 「取消本地需求单」是**删除**本地单，还是**新增"已取消"状态**保留记录？（当前 `requests.status` 只有 草稿 / 待下单 / 已下单，没有"已取消"，需要新增状态值或复用删除逻辑。）
4. 草稿且无下游引用的单，是否要自动取消（默认不自动）？
5. 首次扩范围同步前，是否需要我先出一份"试运行影响清单"（预计新建多少张单、涉及哪些批次/国家）？
