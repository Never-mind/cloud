# 需求单远端取消联动与"不同步原因"登记方案

编写日期：2026-09-11
关联方案：`2026-09-11-demand-sync-status-scope-and-cancel-design.md`、`2026-09-11-request-remote-status-design.md`

## 一、已确认的前提

1. 建档状态放开为 7 种：Issued to Supplier、Confirmed、Committed、Handed Over、Shipped、Arrived、Received；
2. Cancelled 也写台账（只记录，不建单，不计入待处理红点）；
3. 远端整单取消 → **本地需求单自动取消**，并登记取消来源。

## 二、自动取消的边界（重要）

本地需求单可能是草稿、待下单或已下单，且下游已有引用（现有数据：239 张单里 222 张已下单，274 行月账单台账、278 条已确认采购明细引用着需求单）。因此自动取消必须分档：

| 本地需求单情况 | 远端整单取消时的处理 |
| --- | --- |
| 草稿 / 待下单，且未被采购、预付款、月账单引用 | **自动取消**（状态置「已取消」），并登记 `cancelReason = remote_cancelled` |
| 已下单，或已被采购/月账单/预付款引用 | **不自动改**，标记「远端已取消（待人工处理）」并计入红点，提示"该需求单已生成采购订单/账单，请在下游处理" |

判定依据直接复用现有 `deleteRequestOrder` 的占用校验（已生成月账单/预付款则拒绝），保证与既有删除策略一致。

## 三、"不同步原因"登记设计（回答你的问题）

需求：以后要能分清"这张单为什么没有同步/不再同步"——是本地人工取消的，还是远端取消导致的。

### 3.1 本地需求单侧

`merge_power_requests` 新增：

| 字段 | 说明 |
| --- | --- |
| `status` | 新增取值 **「已取消」**（与 草稿 / 待下单 / 已下单 并列） |
| `cancelReason` | `remote_cancelled`（远端取消自动联动）/ `local_manual`（本地人工取消）/ `local_deleted`（本地删除） |
| `cancelledAt` / `cancelledByName` | 取消时间与操作人（远端自动取消时记"系统同步"） |
| `remoteStatus` | 远端履约状态（见上一方案），取消后为 `Cancelled` |

取消后**保留下载记录**（不物理删除草稿），这样"为什么没了"永远查得到；确需删除的仍走现有删除入口（会做下游占用校验）。

下游影响：月账单/预付款/实例结差候选列表现在只排除「草稿」，需要改成**同时排除「已取消」**（一处常量集中处理）。

### 3.2 同步台账侧

台账每条明细新增 `reasonCode`（结构化原因，便于筛选与统计），取值：

| reasonCode | 含义 | 触发场景 |
| --- | --- | --- |
| `created` | 已建档 | 本次创建了本地需求草稿 |
| `local_exists` | 本地需求单已存在 | 未覆盖 |
| `remote_changed` | 远端已变更待核对 | 内容 diff 命中 |
| `blocked_mapping` | 映射未完成 | 供应商/实例型号映射未确认 |
| `remote_cancelled` | 远端已取消 | 远端状态为 Cancelled |
| `local_cancelled` | 本地已取消/已删除 | 本地单被人工取消或删除，远端仍可建档 |
| `out_of_scope` | 状态不在同步范围 | 未知新状态 |

台账列表新增「原因」列（中文展示），并支持按原因筛选——这就是你要的"不同步原因"。`errorMessage` 继续承载详细文本（含 diff 内容）。

## 四、远端取消后又改回 Received，会不会重新抓取？

**当前机制下分两种情况**（这也是要改的点）：

| 情况 | 现状 | 目标行为 |
| --- | --- | --- |
| 本地单**已被删除**（物理删除） | 台账明细若为 `cancelled`，不在"已跟踪"集合里 → **会重新创建** | 保持：重新抓取并建档 |
| 本地单**已取消但记录还在**（新方案的默认做法） | `requestExists` 命中 → 会判"本地需求单已存在，未覆盖" → **不会重建** | 需要改：见下 |

**目标行为（建议）**：远端从 Cancelled 恢复到任一建档状态时：

1. 若本地单是「已取消」且 `cancelReason = remote_cancelled`（即当初是跟着远端取消的）→ **自动恢复**：状态改回「草稿」，清空取消字段，台账明细回到可建档状态，并在同步结果里提示"远端已恢复，已恢复本地需求单"；
2. 若本地单是「已取消」但 `cancelReason = local_manual`（人工取消）→ **不自动恢复**，只提示"远端已恢复，但本地为人工取消，请人工确认"；
3. 若本地单已下单或已被引用 → 只提示，不自动改。

这样"取消—恢复"是对称的，并且始终尊重人工操作。

## 五、实施步骤与工作量

| 步骤 | 内容 | 预估 |
| --- | --- | --- |
| 1 | 状态分流（7 种建档 + Cancelled 记台账）+ 远端状态聚合写入 | 1 天 |
| 2 | `requests` 新增「已取消」状态与取消字段 + 迁移脚本 | 0.5 天 |
| 3 | 自动取消联动（含下游占用校验分档） | 0.5 天 |
| 4 | 台账 `reasonCode` + 原因列与筛选 | 0.5 天 |
| 5 | 远端恢复自动/人工恢复逻辑 | 0.5 天 |
| 6 | 财务候选列表排除「已取消」+ 采购确认的远端取消校验 | 0.5 天 |
| 7 | 试运行影响清单核对 + 回归测试 | 1 天 |

合计约 **4.5 天**，可分两批上线（第 1–4 步约 2.5 天先解决"状态范围 + 取消登记"，第 5–7 步再做恢复与校验）。

## 六、待确认

1. 自动取消时，本地单是**保留为「已取消」状态**（推荐，可追溯）还是**直接删除草稿**（历史记录会丢）？
2. 远端恢复时，对"跟远端取消的本地单"是否要**自动恢复为草稿**（推荐）？人工取消的是否只提示？
3. 首次放开 7 种状态同步前，是否先出一份「试运行影响清单」（预计新建多少张单、涉及批次/国家），核对后再正式执行？
