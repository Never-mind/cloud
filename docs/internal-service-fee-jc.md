# 管理费：JC历史差额调整

入口：**算力系统 → 财务管理 → 管理费 → 管理费调整单 → JC管理费核定与历史差额调整**。管理费分摊页也提供入口。沿用管理费模块的可见性与权限配置，不自动开放其他模块。

## 初始化和候选记录

- 初始化按每条合同实例识别，不按批次整体识别。同一批次有多条实例时，已初始化实例出现在分摊页，其他实例仍可在待初始化页出现；页面显示合同实例总数、已初始化和待初始化数量。
- 自动生成的分摊明细是计算计划，不等于已登记历史或已确认对账单。查看页面不会初始化剩余实例，也不会覆盖已有月度数据。
- JC列表来自已确认的“实例合同调整单”，即合同价格调整。未核定的候选也会显示，但状态是“待核定”，不代表管理费已确认。列表中的号码明确标为“来源合同调价单号”。
- 管理费区间调整是另一类单据，来自管理费分摊页的人工月度金额调整，与来源合同价格调整分开维护。
- 已初始化实例如果存在已确认的实例合同调价，必须生成独立 JC；原实例不再吸收该调价。新增 JC 尚未核定时，相关国家不能生成管理费对账单。

## 计算口径

- 每个“月账单合同＋已确认调整单明细”对应一条独立JC，记录来源调整单、原合同和原合同结束月份。相同设备编码不会作为唯一身份。
- 原实例保持原合同口径；JC只计算受影响的前24个月单价变化，乘受影响数量并除税。后36个月价格变化不计入JC总额，也不再次扣采购成本。
- 后36个月仍属于分摊区间。剩余金额平均分配到用户选择的恢复月份至原合同第60个月内的开放月份，最后一个月吸收分币尾差。
- 金额按**原合同币种**展示和登记。界面明确标明币种，不会把人民币合同金额标作美元；历史表若使用USD，应先按已核定合同汇率换算为页面币种。
- 合同币种与采购币种不一致时，先用固定合同汇率把采购成本折到合同币种再计算管理费。BR 的 CNY 合同、USD 采购不再直接相减。
- 每份管理费台账同时保存原币金额、报告币种、折算汇率和报告币种金额。报告金额用于 USD 汇总，不覆盖原币审计金额。
- 附件导入的备件以独立备件台账和 `sourceType=spare` 月度明细存在，不混入原实例或 JC。

## 使用步骤

1. 搜索对应JC，点击“查看／调整”打开弹窗。先核对来源、币种、规则总额与原合同结束月。
2. 如有已登记历史，在“历史月度登记”逐月填入真实登记金额和原因。允许0和负数；保存后只锁定该月。不会依据2026年10月这个测算假设自动锁定所有历史。
3. 输入**全周期核定总额**，不是剩余未计金额；填写原因，例如“历史后36个月设备数量口径差异，经核对按原表总额延续”。
4. 选择恢复分摊月份，点击弹窗底部固定的“计算预览”，核对月度金额后点击“确认管理费调整”。修改输入后需重新计算预览。

确认时固定保存：

`固定历史差额 = 全周期核定总额 − 确认时规则总额`

之后的金额为：

`当前可结算总额 = 当前规则总额 + 固定历史差额`

`待分摊金额 = 当前可结算总额 − 累计已登记／已对账金额`

后续合同调价会形成新的JC增量，原固定历史差额不会被重新计算抵销。再次人工核定前先退回；退回和重新确认都会产生审计记录，保留前后值、原因、操作人和时间。

## 确认与退回

- JC核定状态为“待核定／已确认／已退回”。已确认的核定金额及分摊月份只读，填写退回原因后点击“退回待核定”，再修改、预览、重新确认。
- 退回不修改来源合同价格；保留已登记历史和已对账月份。未锁定月份暂时按规则余额重算，原核定总额和分摊月份作为待修改方案保留，固定历史差额待重新确认后生效。
- JC退回后，相关国家暂不能生成新的管理费对账单，避免把未核定余额当成最终金额。
- 管理费区间调整单可“查看／调整 → 退回草稿 → 修改 → 确认调整”。若已有对账月份使用该区间调整，不能退回或撤销，应在后续开放月份另建调整。
- 这些状态沿用现有确认时间、核定总额和区间调整状态字段推导，无需为退回功能增加数据库字段。

例如（示意）：USD规则总额−59,315.20，核定总额−53,899.04，则固定历史差额为+5,416.16。对应原币规则总额和核定总额分别保存在组件的原币字段中。

## 到期和历史保护

- 已到期合同必须明确选择开放月份一次性结清余额，不能再把差额摊回过去的未登记月份。
- 若新JC到期后尚未指定结清月，列表显示“待指定结清月”和未分配金额；未处理前不能生成相关国家的管理费对账单，避免漏计。
- 已登记／已对账月不能覆盖。需要纠正时，通过后续开放月调整，保留历史链路。
- 初次切换独立JC时，若旧版管理费已有合并对账或人工登记，系统要求先核对原实例和JC拆分，避免重复计算；不会自动把旧合并记录当成原实例或JC。
- 有独立JC记录的原合同不能直接删除／更换，原调价单不能退回草稿；后续变化通过新调整单处理。
- 这次提供JC逐月登记与核定入口，不会自动导入Excel、替用户核定差异，亦未添加备件档案导入功能。

## 部署

新增三张表，不修改原财务数据：

- `merge_power_internalservicejccomponents`：规则基数、核定总额、固定差额、来源及分摊月份。
- `merge_power_internalservicejcmonths`：JC月度登记／分摊及锁定状态。
- `merge_power_internalservicejcaudit`：操作历史及前后值。

JC月度明细也写入现有 `merge_power_monthlyinternalservicefees`，以独立JC身份保留每月唯一性，并沿用管理费对账单。`jc`表示分摊，`jc_history`表示锁定历史。原账单合同仍通过JC组件中的`ledgerId`关联。

已有环境先确认数据库目标并按部署制度备份，然后运行专用增量迁移：

```powershell
npm run schema:internal-fee-jc
npm run schema:internal-fee-jc -- --apply
```

第一条只显示计划，第二条创建缺失表，可重复执行。随后构建并重启服务。无需执行全量迁移、seed或历史回填。新环境的`schema.sql`和初始化迁移也包含新表。管理费模块默认关闭时，需要管理员在模块配置中启用管理费相关入口并分配权限。

报告币种字段的增量迁移：

```powershell
npm run schema:internal-fee-reporting
npm run schema:internal-fee-reporting -- --apply
```

历史合同调价需要从原实例拆为独立 JC 并整批重建时，先运行只读预检，再显式执行：

```powershell
npm run internal-service-fees:reinitialize
npm run internal-service-fees:reinitialize -- --apply
```

重建脚本会拒绝在已有对账快照或已确认管理费区间调整时执行，并先把台账、月明细、调整单、快照和 JC 数据复制到带时间戳的备份表。

需要替换历史归档时显式增加 `--replace-archives`。历史冻结范围可用 `--archive-through=YYYY-MM` 指定；批量归档不会再逐月重算全部实例。
